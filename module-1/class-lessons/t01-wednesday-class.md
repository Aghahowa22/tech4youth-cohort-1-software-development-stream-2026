## **Topic 01 - Learning Objectives**

By the end of this topic, learners will be able to:

- ✅ Identify the main roles on a software team and describe what each person is responsible for
- ✅ Explain the Software Development Lifecycle (SDLC) as a sequence of phases from idea to maintenance
- ✅ Compare traditional (Waterfall) delivery with iterative (Agile) delivery
- ✅ Describe the core Agile principles and how the Scrum framework puts them into practice
- ✅ Write user stories in the "As a / I want / so that" format
- ✅ Create acceptance criteria using the Given/When/Then format
- ✅ Format documentation using Markdown syntax
- ✅ Understand branches, pull requests, and responsible AI use in software development

## **T01 - L2: Agile Frameworks & Scrum in Practice**

### **Date:** September 18, 2026 (Wednesday)
### **Duration:** 2 hours
### **Key Sections Covered:**

1. **The Agile Manifesto and Principles**
   - Individuals and interactions over processes and tools
   - Working software over comprehensive documentation
   - Customer collaboration over contract negotiation
   - Responding to change over following a fixed plan

2. **Introduction to Scrum Framework**
   - Scrum Roles: Product Owner, Scrum Master, Development Team
   - Scrum Artifacts: Product Backlog, Sprint Backlog, Increment
   - Scrum Ceremonies (Events):
     - Sprint Planning
     - Daily Standup (Daily Scrum)
     - Sprint Review
     - Sprint Retrospective

3. **Understanding Sprints**
   - What is a sprint (typically 1-2 weeks)
   - How work flows through a sprint
   - The definition of "done"

4. **Other Agile Frameworks**
   - Kanban: visualizing work without fixed sprints
   - Lean principles
   - Hybrid approaches

5. **Putting It All Together: Roles + SDLC Phases + Scrum Running in Parallel**
   - How different pieces of work sit in different SDLC phases simultaneously
   - Real-time workflow on a real Agile team

### **Learning Activities:**

- [ ] Scrum ceremony demonstrations
- [ ] Sprint flow walkthrough
- [ ] Role-playing exercise: Plan a sprint
- [ ] Discuss: What happens in a standup meeting?
- [ ] Create a sample backlog for a project

### **Key Takeaways:**

> **Scrum** is one popular framework for practicing **Agile** values. It organizes work into **sprints** (fixed time periods) with clear **ceremonies** (meetings), **roles** (PO, Scrum Master, team), and **artifacts** (backlog, increment). On a real team, all SDLC phases happen in parallel, with different features at different stages simultaneously.

## **T01 - L3: User Stories, Acceptance Criteria & Documentation**

### **Date:** September 18, 2026 (Wednesday)
### **Duration:** 2 hours
### **Key Sections Covered:**

1. **User Stories**
   - Definition: A short, plain-language description of work from the user's perspective
   - Template: "As a [type of user], I want [goal], so that [reason/benefit]"
   - Why user stories matter in Agile teams
   - The INVEST criteria: Independent, Negotiable, Valuable, Estimable, Small, Testable

2. **Acceptance Criteria**
   - Definition: Specific, testable conditions that prove a story is done
   - Given/When/Then format (Gherkin style)
   - Bullet-checklist format
   - Creating clear, testable criteria

3. **Markdown Formatting**
   - Headers (#, ##, ###, etc.)
   - Bold and italic (**text**, *text*)
   - Lists (ordered and unordered)
   - Links [text](url)
   - Code blocks and inline code
   - Tables
   - Why Markdown is essential for developer documentation

4. **Branches and Pull Requests**
   - What branches are and why they're used
   - The feature branch workflow
   - Creating and reviewing pull requests
   - Code review best practices
   - Merging code safely

5. **Responsible AI Use**
   - Verification: Always check AI-generated content
   - Data privacy awareness: Don't share sensitive information
   - Disclosure: Be transparent when using AI tools
   - Best practices when using AI to draft stories, code, or documentation

### **Learning Activities:**

- [ ] Write user stories from provided scenarios
- [ ] Create acceptance criteria using Given/When/Then
- [ ] Format a plain-text document into readable Markdown
- [ ] Practice GitHub branch and PR workflow (demo or hands-on)
- [ ] Group exercise: Review and improve poorly-written user stories
- [ ] Discuss responsible AI practices in your workflow

### **Key Deliverables:**

- [ ] At least 3 well-written user stories
- [ ] Acceptance criteria for each story
- [ ] A formatted Markdown document demonstrating all syntax
- [ ] Understanding of branch/PR workflow

### **Resources:**

- 📚 Markdown Cheat Sheet: https://www.markdownguide.org/cheat-sheet/
- 🔗 GitHub Branches & PRs Guide: https://docs.github.com/
- 🤔 AI Safety Practices: https://www.anthropic.com/research

### **Key Takeaways:**

> **User stories** capture user needs (not technical solutions) in a format everyone understands. **Acceptance criteria** define the checklist for "done." **Markdown** makes documentation readable and shareable. **Branches and PRs** keep code organized and reviewed. **Responsible AI** means verification, privacy, and transparency when using AI tools in your workflow.

## **Key Glossary - Topic 01**

| Term                    | Definition                                                                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **SDLC**                | Software Development Lifecycle — the phases software moves through (Planning → Design → Development → Testing → Deployment → Maintenance) |
| **Agile**               | A mindset/approach favoring small iterations, collaboration, and adapting to change                                                       |
| **Waterfall**           | A linear approach where each SDLC phase is completed before the next begins                                                               |
| **Scrum**               | A specific framework for practicing Agile, organized into sprints with defined roles and ceremonies                                       |
| **Kanban**              | An alternative Agile framework focused on visualizing work and limiting work-in-progress                                                  |
| **Sprint**              | A fixed time period (often 1–2 weeks) in Scrum during which committed work is completed                                                   |
| **Backlog**             | A prioritized list of work (Product Backlog = everything; Sprint Backlog = this cycle's work)                                             |
| **Product Owner (PO)**  | The person who owns the backlog and decides what gets built and in what order                                                             |
| **Scrum Master**        | The person who facilitates the Scrum process and removes blockers                                                                         |
| **User Story**          | A short description of work from the user's perspective (format: "As a..., I want..., so that...")                                        |
| **Acceptance Criteria** | Specific, testable conditions that must be true before a story is considered done                                                         |
| **Markdown**            | A lightweight markup language for formatting plain text into readable documentation                                                       |
| **Branch**              | An isolated copy of code where you can work without affecting the main codebase                                                           |
| **Pull Request (PR)**   | A request to review and merge changes from one branch into another                                                                        |
| **MVP**                 | Minimum Viable Product — the smallest working version that delivers real value                                                            |
| **Standup**             | A short, daily team sync meeting (typically 15 minutes)                                                                                   |
| **Retrospective**       | A team meeting to reflect on what went well and what to improve                                                                           |
| **Technical Debt**      | Shortcuts taken during development that will need fixing later                                                                            |

## **Knowledge Check - Topic 01**

### **Scenario Practice:**
You've just joined a team building a mobile budgeting app. It's Wednesday of a two-week sprint.

1. The Product Owner is finalizing requirements for next sprint's "spending alerts" feature
2. A developer just finished coding the "recurring bills" feature and handed it to QA
3. You're in your daily standup

**Answer these questions:**

- [ ] What is the name of the meeting you're in, and what is its purpose?
- [ ] Which SDLC phase is "spending alerts" in? Which phase is "recurring bills" in?
- [ ] Is this team using Waterfall or Agile? What evidence tells you that?
- [ ] If you're the Scrum Master and a teammate is blocked waiting on a design file, what do you do?
- [ ] Explain the difference between Product Backlog and Sprint Backlog using this scenario

## **Instructor Notes**

- **T01 L1 pace**: Give extra time for the "roles" discussion — beginners often have assumptions about what jobs exist in tech
- **T01 L2 emphasis**: The hardest concept is seeing *all* SDLC phases happening in parallel. Use concrete examples (Feature A in testing, Feature B in coding, Feature C in requirements planning — all on the same day)
- **T01 L3 focus**: Spend time on user stories. Many learners want to write technical solutions; remind them that "as a user, I want" is *always* about value, never about implementation
- **Breakout activity**: Have learners write user stories for something they know (e.g., a restaurant app, a school system) and peer-review them using the INVEST criteria
